# 追従制御・エッジAI（顔）・クラウドLLM（Sarashina/Gemini）を組み合わせた、小型ロボットの環境認識と応答制御

リポジトリ: https://github.com/wwlapaki310/stackchan-responsive-ai （MIT）　／　動画: {{VIDEO_URL}}

## 1. 概要と目的

小型ロボット（M5Stack Stack-chan K151、ESP32-S3）では、画像の意味を理解するような重い認識は載せられない。一方、クラウドのLLM/VLMは、状況を理解して説明できるが、遅く、画像を外へ出す必要がある。そこで、**認識を、本体（エッジ）とクラウドで役割分担**させた。

- 本体で分かること（顔の有無・向き・音量・動き）は、本体だけで処理し、首の追従制御に使う。
- 本体で分からないこと（何をしているか、何を持っているか）だけを、クラウドへ聞く。
- 本体とWi-Fiとクラウドだけで動く（PC側の中継は使わない）。

## 2. 動画で見せていること

1. ブラウザから質問すると、Sarashina（LLM）が約0.6秒で答え、字幕で出す。
2. 「監視モード」で、首を左右±110°まで振って人を探す。
3. 本体の顔検出で人を見つけ、首を向けて追い、挨拶する。回答を待つ間も、追従と相づちを続ける。
4. 「見て」で、カメラ1枚をGemini（VLM）へ送り、状況の説明文を字幕と声で返す。
5. 「判断」ボタンで、本体のみ／「見て」のときだけクラウド、を切り替える。
6. 大きな音（拍手）に反応する（音量だけを見る。録音しない）。

## 4. 工夫した点

- **役割分担と選択**: エッジ（顔検出 pico、動き検出、音量認識）とクラウド（Sarashina、Gemini）を分け、画像をクラウドへ送るかどうかを、ブラウザの「判断」で選べる。既定は、送らない。自動の画像送信は、1分に1回までに制限した。
- **追従制御**: 顔の位置から首（yaw）を向ける閉ループ制御を、比例制御から積分制御に変えた。シミュレーション（画角60°とサーボ速度90°/sは仮定）で比べ、比例制御で残る定常偏差を、積分制御が消すことを確認した。実機での効果は未検証。
- **追従方式の選択**: 顔検出／動き（フレーム差分）／顔→動き、を切り替えられる。
- **遅着・取消・失敗に強い設計**: 要求IDで、取り消し済みや古い応答を捨てる。通信の失敗（誤キー、到達不能、ハング）のあとも、次の質問が成功した（故障注入で確認）。調停の部分は、ハード非依存のC++17で書き、ホストテストで意味論を確認した。
- **プライバシー**: 音声は録音も送信もしない。画像は、「見て」のときの1枚だけで、保存もログもしない。

## 5. 実機での確認結果（K151、2026-10-30）

数値は、条件を統制していない作業時の記録で、評価値ではない。

| 項目 | 結果 |
|---|---|
| 自律の流れ | 顔検出 → 挨拶 → 自分から質問 → 回答、が通った（ログ、ダッシュボードの記録） |
| Sarashinaの応答 | 31回の質問がすべて成功。526〜806 ms（平均602 ms） |
| 「見て」（画像→Gemini） | 約4〜8秒が大半、最大約14秒（時間切れの回もある）。説明文は、画像の内容に合っていた（目視） |
| 顔検出 | 約10〜14fps。検出率は低い（正面の顔のみ） |
| 通信失敗からの回復 | 誤キー・到達不能・ハングのあと、次の質問が成功 |

## 6. 限界と今後

- 顔検出の検出率は低い（正面の顔だけ）。追従は、yawのみ。ユーザー実験や、比較実験は、していない。
- 読み上げや「見て」を繰り返すと、本体が再起動することがある。原因は未特定（メモリ破損の疑い）。
- 今後: 本体で動く小さな検出器の追加、再起動の原因の特定、追従制御の実機評価。
