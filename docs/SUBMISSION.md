# Stack-chan Responsive AI: 説明資料

**追従制御・エッジAI（顔）・クラウドLLM（Sarashina/Gemini）を組み合わせた、小型ロボットの環境認識と応答制御**

- リポジトリ: https://github.com/wwlapaki310/stackchan-responsive-ai （MITライセンス）
- デモ動画: https://youtu.be/MchQt4YmAqU
- 状態: 2026-10-30時点の作業版。評価実験は未実施。論文（`paper/`）は作業草稿で、完成した研究ではない。

## 1. 何を作ったか

M5Stack Stack-chan（K151、CoreS3）に、次の動きをさせた。

1. 誰もいないとき、首を左右に大きく振って人を探す（監視モード）。
2. 本体上の顔検出で人を見つけ、首を向けて追い、声で挨拶する。
3. 人の前にしばらくいると、自分からクラウドのAI（Sarashina）に質問する。
4. **回答を待つ間も**、顔の追従、「えーっと」の相づち、タッチへの反応を止めない。
5. 本体で分からないこと（何をしているか、何を持っているか）は、カメラ1枚をクラウドの画像対応AI（Gemini）に見せ、状況の説明文を字幕と声で返す。
6. 本体で分かること（顔の有無、向き、音量）は、本体だけで処理する。クラウドへ送るかどうかは、ブラウザの画面から選べる。

通常の動作は、本体、Wi-Fi、クラウドAPIだけで完結する（PCのプロキシは使わない）。

## 2. 問題設定

小型ロボットのMCU（ESP32-S3）では、重い認識（画像の意味の理解）は載せられない。一方、クラウドのLLM/VLMは、何が起きているかを理解できるが、遅く、画像を外へ出す必要がある。そこで、**認識を、本体とクラウドで役割分担する**構成を作る。

- 本体で分かること（顔の有無・向き・音量・動き）は、本体だけで処理し、首の追従制御に使う。
- 本体で分からないこと（何をしているか、何を持っているか）だけを、クラウドのVLM（Gemini）へ聞く。送るのは、1枚の画像で、使うときだけ選べる（既定オフ）。
- 文章の応答は、LLM（Sarashina）で行う。
- クラウドの応答が遅れる・失敗する・取り消されても、ロボットは止まらず、古い応答は捨てる（補足: 待っている間も、追従・相づち・タッチ反応を続ける）。

顔追従そのものは、新しい技術ではない（M5Stack公式にも、UiFlow2の顔追従サンプルがある）。ここで示すのは、**エッジAI・追従制御・クラウドLLM/VLMの組み合わせ方と、遅着・取消を含む調停の構成**である。ユーザー実験はしていないので、自然さ、愛着、待ち時間の短縮は、主張しない。

## 3. 構成

```
カメラ ─▶ 顔検出(pico) / 動き検出 ─▶ 追従制御(積分) ─▶ サーボ(yaw)
マイク ─▶ 音量だけ                      │
タッチ ─▶ 反応                           ▼
              portable core: Interaction（状態・鮮度・取消） + Director（自律動作の方針）
                                         │ キュー
                       apiTask ──HTTPS──▶ Sarashina（文章）／Gemini（画像・読み上げ）
```

- `loop()` だけが、ポータブルなコア（`include/`）を呼ぶ。HTTPSは別タスクで、キューだけでやり取りする。
- コアは、ESP-IDF・Arduino・ハードに依存しないC++17のヘッダのみで、ホストテストで意味論を検証している。
- 詳細は [docs/ARCHITECTURE.md](ARCHITECTURE.md)。

## 4. 3つの観点

### ロボティクス工学
- 顔の位置から首（yaw）を向ける**閉ループの追従制御**。比例制御から積分制御に変え、顔を中央へ寄せ続けるようにした。
- 比較は、**シミュレーションのみ**（[docs/sim](sim/README.md)、`tools/track_sim.py`）。画角60°とサーボ速度90°/sは**仮定**。結果: 比例制御は、定常偏差が残る（`step`で約10°）。積分制御は偏差を消す。ゲインが高いほど速い（`step`で中心±3°に入る中央時間は、G=40/80/160で3.1/1.2/0.5秒）。順位は、画角50〜80°、速度45〜180°/sの範囲で変わらなかった。実機での効果は未検証。
- 追従方式を、画面から選べる（顔検出／動き（フレーム差分）／顔→動き）。
- 監視モード: 首を±110°まで、約40°/秒で往復する。実機で動作を確認した。

### AI処理
- **本体のAI**: 顔検出（pico）、動き検出、音量の認識。画像・音声は、本体の外に出ない。
- **クラウドのAI**: 文章の応答はSarashina、画像1枚の解釈と読み上げはGemini。
- **振り分け**: 本体で分かることは本体で処理し、分からないことだけクラウドへ送る。「判断」ボタンで、本体のみ／「見て」のときだけ／常に、を選べる。自動の画像送信は、1分に1回までに制限した。

## 5. 実機で確認したこと

実機は、K151（COM3）。根拠は、シリアルログ、ダッシュボードの画像、`tools/` の確認スクリプト。数値は、条件を統制していない作業時の記録で、評価値ではない。

| 項目 | 結果 |
|---|---|
| 顔検出の速さ | 本体の1フレームの処理は、約10〜14fps（画像取得・描画を含む） |
| 顔検出の検出率 | 低い。顔が前にある間に約4〜50%（条件を統制していない）。正面の顔だけ |
| 自律の流れ | 顔検出 → 挨拶 → 自分から質問 → 回答待ちの間も追従・相づち → 回答の字幕、が通った（ダッシュボードの記録、ログ） |
| Sarashinaの応答 | 31回の質問で、全部成功（HTTP 200）。526〜806 ms、平均602 ms（読み上げオフ） |
| 通信失敗からの回復 | 誤キー（401、0.9秒）、到達不能（-1、5.5秒）、ハング（15.4秒で「時間切れ」）のあと、次の質問が成功した（`tools/fault_check.py`） |
| 取消・遅着の拒否 | 確認済み（`tools/web_check.py`） |
| 「見て」（画像→Gemini） | 十数回実行。画像の解釈の応答は、約4〜8秒が大半で、最大約14秒（1回は時間切れ）。説明文は画像の内容に合っていた（目視） |
| 読み上げ（Gemini TTS） | 動作確認。無料枠の回数制限（429）や接続失敗の回があり、その回は字幕だけになる |
| 監視モード | 首が±110°を往復することを、ログで確認（目視は作者） |
| マイク反応 | 音量の記録（ダッシュボードの「音」）を確認。首が止まっているときだけ反応する |

## 6. 限界と、正直に書くこと

- **再起動**: 読み上げや「見て」を繰り返すと、本体が再起動することがある（約15回で3回、別の直近の4回では0回）。ヒープ破損が疑われるが、原因は特定していない。
- 顔検出の精度が低い。正面の顔だけで、照明や距離の影響が大きい。
- 追従は、yaw（左右）だけ。pitch（上下）は未実装。
- 追従制御の比較は、シミュレーションで、実機の効果は未検証。
- 待ち時間は、Sarashinaでは約0.6秒と短い。待機中の動作が目立つのは、画像の解釈（数秒）のときである。
- 比較用のベースライン（待機中に止まる方式）との、実機での対照実験は、していない。ユーザー実験もしていない。
- 画像をクラウドへ送る機能は、既定でオフ。送るのは、「見て」のとき（または「常にGemini」のとき）の1枚だけで、保存もログ出力もしない。Geminiの無料枠では、送った内容がサービスの改善に使われうる。

## 7. プライバシーとデータの扱い

- APIキー、Wi-Fi情報は、git管理外のファイル（`secrets.h`）に入れる。リポジトリには含めない。
- クラウドへ送るのは、質問・回答の文章、本体が作る状況の一行（顔が見えている時間、向き、大きな音の有無）、「見て」のときの画像1枚。**音声は送らない。**
- 画像・音声は、本体で保存しない。ログには、質問の文面を出さない。
- ダッシュボードは、同じLAN内の平文HTTP＋トークン。公開しない。

## 8. 再現の手順

READMEの「動かす」を参照。要るもの: K151、arduino-cli、ESP32コア3.3.11、各ライブラリ、Python 3、APIキー（Sarashina、任意でGemini）。ホストテストは、`g++ -std=c++17 -Wall -Wextra -Werror -pedantic -Iinclude tests/host.cpp -o stackchan-host`。ホストテストは、ポリシーの意味論だけを検証し、実機のタイミング、AI、通信は証明しない。
