# 構成の詳細

対象: `firmware/answer_demo/answer_demo.ino`（本体のメインのスケッチ）と、`include/`のポータブルコア。実機で確認していない項目はREADMEの「確認状況」を参照。

## 1. タスクと所有者

| 実行単位 | 役割 | 触るもの |
|---|---|---|
| `loop()`（Arduinoのメインタスク） | カメラ取得、検出、追従制御、コア・Directorの呼び出し、サーボ、画面、スピーカー、マイク、Web | **すべて**。コアを呼べるのはここだけ |
| `apiTask`（コア0に固定、スタック16KB） | HTTPS（LLM、任意でTTS）だけ | ネットワーク。コア・画面・スピーカー・サーボには触らない |

`loop()`と`apiTask`は、FreeRTOSのキューだけでやり取りする（要求キュー: 長さ1、結果キュー: 長さ2）。Webのハンドラーも`web.handleClient()`の中、つまり`loop()`の文脈で動くので、コアの単一所有は崩れない。

## 2. ポータブルコア（`include/`）

- `Interaction`: 要求ID、状態（待機・回答待ち・回答中・中止・エラー）、観測の鮮度（500 ms）、タッチ表情（400 ms）、タイムアウト（15 s）。古い要求・キャンセル済みの要求の結果は拒否する。顔を見失っただけでは要求をキャンセルしない。首の追従と画面の表情は独立に決める。
- `Director`: 挨拶（顔が現れた）、自分からの質問（約3秒追従したあと、30秒のクールダウン）、相づち（待ち始めて1.5秒後、以降3秒おき、最大2回）、「だれか」（長い無人）を決める。入出力は持たず、返した行動を呼び出し側が実行する。逆行する時刻は無視する。

どちらもC++17のヘッダのみで、`tests/host.cpp`で検証している（意味論のみ）。

## 3. 追従のパイプライン

```
カメラ(RGB565 320x240) ─▶ 160x120のグレー化（バイト順の入れ替えが必要）
   ├─ 顔検出（pico、約15 ms/フレーム）  ┐
   └─ 動き検出（4x4セルのフレーム差分）  ┴▶ 検出位置 x∈[-1,1]
       ─▶ 平滑化 ─▶ core.observe() ─▶ 積分制御 ─▶ サーボ指令（100 msごと、yaw ±45°に制限）
```

- **追従方式**（Webで切り替え）: 顔検出 / 動き / 顔→動き（顔が見つからないときだけ動きを使う）。動き検出はカメラが頭と一緒に動くため、首を動かした直後350 msのフレームは使わない。画像の35%以上が変わるとき（照明のちらつきなど）も無視する。
- **積分制御**: 検出のたびに`yawTarget += int(smoothX * 80)`（0.1°単位、不感帯0.08）。比例方式（旧）との比較は[sim/README.md](sim/README.md)（シミュレーションのみ）。
- 検出が途切れても、観測の鮮度（500 ms）が切れるまでは追従中とみなし、切れたあと3秒は首を動かさない。そのあとは、自律モードなら±25°の見回し、そうでなければ正面へ戻る。

## 4. 音声（スピーカーとマイク）

CoreS3では、スピーカーとマイクが同じ音声ポートを共有し、同時に使えない。話すときは、マイクを止めてスピーカーを動かし、話し終えて600 ms後にマイクを再開する（自分の声を拾わないため）。マイクは16 kHzで256サンプルごとに平均絶対偏差だけを計算する。背景の音量を適応的に推定し、「背景×3＋250」を超えたら「音」のイベントとして、表情を変え、回答待ちでなければ声を出す。**音声データは保存も送信もしない。**

固定フレーズは、PCで事前に合成して配列として埋め込む（`tools/gen_voice.py`、16 kHz）。任意で、回答をOpenAI TTS（PCM、24 kHz）で読み上げられる。PSRAMに最大8秒分を置き、再生が終わるまで次の取得を待たせる。

## 5. Web操作画面（LAN、平文HTTP、トークン）

| エンドポイント | 内容 |
|---|---|
| `GET /` | 操作画面（トークンなしでも表示。操作はトークンが必要） |
| `GET /status` | 状態、首の角度と目標、検出のfps、API時間、音量、直近のイベント、各オプション |
| `POST /ask` `/cancel` `/touch` `/view` `/stream` | 質問、中止、タッチ反応、本体の表示切替、カメラ配信 |
| `POST /opt?n=auto\|mute\|tts\|mic\|mode` | 自律、消音、読み上げ、マイク、追従方式の切り替え |
| `POST /opt?n=fault&v=0..3` | **試験用の故障注入**（誤キー、到達不能、ハング）。`tools/fault_check.py`が使う |
| `GET /snap` | カメラ配信がオンのときだけ、現在の1フレームをJPEGで返す（保存しない） |

操作系はすべて`?t=<トークン>`が必要で、トークンは`tools/gen_secrets.ps1`が生成する。TLSはない。信頼できるLANだけで使う。インターネットへ公開しない。

## 6. セキュリティとデータの扱い

- APIキー、Wi-Fi情報、トークンは`firmware/answer_demo/secrets.h`（git管理外）に入る。ログには質問の文面を出さない（IDとタグだけ）。
- クラウドへ送るのは、質問の文面（自律の質問には「顔が見えている時間・向き・大きな音の有無」を一行にした状況文が付く）と、読み上げを使う場合は回答の文面。音声は送らない。**カメラ画像は、既定では送らない。** ダッシュボードで「視覚」をオンにし、「見て」か自律の質問が起きたときだけ、1枚のJPEGをGemini APIへ送る（RAMのみ、保存・ログなし、無料枠ではデータが改善に使われうる）。カメラ配信はLAN内のブラウザへだけ出る（既定オフ）。
- クラウドとのTLSは、Sarashinaでは証明書を固定して検証し、OpenAIでは同梱の証明書バンドルで検証する。

## 7. 既知の制約

- 顔検出（pico）は正面の顔だけを検出し、検出率は低い。動き検出は、首が動いている間は使えない。
- 首の追従はyawのみ。pitchは未実装（コアの拡張が要る）。
- 公式のAIエージェントのファーム（音声認識を含む）とは別のファームで、併用していない。
- 待ち時間は、Sarashinaの応答が速い（約0.7秒）ため、短い。
